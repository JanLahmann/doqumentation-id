Iskay Quantum Optimizer oleh Kipu Quantum

Lihat referensi API

Catatan
  • IBM Quantum® Functions adalah fitur beta yang hanya tersedia untuk pengguna IBM Quantum Premium Plan, Flex Plan, dan On-Prem (melalui IBM Quantum Platform API) Plan. Fitur beta dapat berubah sewaktu-waktu.

Gambaran Umum​

Dengan Iskay Quantum Optimizer dari Kipu Quantum, kamu bisa menangani masalah optimasi yang kompleks menggunakan komputer kuantum IBM®. Solver ini memanfaatkan algoritma bf-DCQO mutakhir dari Kipu yang hanya membutuhkan fungsi objektif sebagai input untuk secara otomatis menghasilkan solusi masalah. Optimizer ini bisa menangani masalah optimasi hingga 156 qubit, sehingga memungkinkan penggunaan semua qubit pada perangkat kuantum IBM. Optimizer menggunakan pemetaan 1-ke-1 antara variabel klasik dan qubit, yang memungkinkan kamu menangani masalah optimasi dengan hingga 156 variabel biner.

Optimizer ini memungkinkan penyelesaian masalah optimasi biner tanpa kendala. Selain formulasi QUBO (Quadratic Unconstrained Binary Optimization) yang umum digunakan, ia juga mendukung masalah optimasi orde tinggi (HUBO). Solver ini menggunakan algoritma kuantum non-variasional, yang menjalankan sebagian besar komputasi pada perangkat kuantum.

Berikut ini informasi lebih lanjut tentang algoritma yang digunakan dan panduan singkat cara menggunakan fungsi ini, beserta hasil benchmark pada berbagai instance masalah dengan ukuran dan kompleksitas yang berbeda-beda.

Deskripsi​

Optimizer ini adalah implementasi siap pakai dari algoritma optimasi kuantum mutakhir. Ia menyelesaikan masalah optimasi dengan menjalankan sirkuit kuantum yang sangat dikompresi pada perangkat keras kuantum. Kompresi ini dicapai dengan memasukkan suku-suku counterdiabatic ke dalam evolusi waktu yang mendasari sistem kuantum. Algoritma ini menjalankan beberapa iterasi eksekusi perangkat keras untuk mendapatkan solusi akhir dan menggabungkannya dengan pasca-pemrosesan. Langkah-langkah ini terintegrasi secara mulus ke dalam alur kerja Optimizer dan dieksekusi secara otomatis.

Bagaimana cara kerja Quantum Optimizer?​

Bagian ini menguraikan dasar-dasar algoritma bf-DCQO yang diimplementasikan. Pengenalan algoritma ini juga bisa ditemukan di saluran YouTube Qiskit.

Algoritma ini didasarkan pada evolusi waktu sistem kuantum yang berubah seiring waktu, di mana solusi masalah dikodekan dalam ground state sistem kuantum di akhir evolusi. Menurut teorema adiabatik, evolusi ini harus berlangsung lambat untuk memastikan sistem tetap berada di ground state-nya. Mendigitalisasi evolusi ini adalah dasar dari komputasi adiabatik kuantum terdigitalisasi (DQA) dan algoritma QAOA yang sudah sangat dikenal (dan kerap diperdebatkan). Namun, evolusi lambat yang diperlukan tidak layak untuk ukuran masalah yang semakin besar karena menghasilkan kedalaman sirkuit yang semakin bertambah. Dengan menggunakan protokol counterdiabatic, kamu bisa menekan eksitasi yang tidak diinginkan yang terjadi selama waktu evolusi singkat sambil tetap berada di ground state. Di sini, mendigitalisasi waktu evolusi yang lebih singkat ini menghasilkan sirkuit kuantum dengan kedalaman lebih pendek dan lebih sedikit gate entangling (gate pembentuk keterkaitan).

Sirkuit algoritma bf-DCQO biasanya menggunakan hingga sepuluh kali lebih sedikit gate entangling (gate pembentuk keterkaitan) dibandingkan DQA, dan tiga hingga empat kali lebih sedikit gate entangling dibandingkan implementasi QAOA standar. Karena jumlah gate yang lebih sedikit, lebih sedikit kesalahan yang terjadi selama eksekusi sirkuit pada perangkat keras. Oleh karena itu, optimizer ini tidak memerlukan teknik seperti penekanan kesalahan atau mitigasi kesalahan. Mengimplementasikannya di versi mendatang dapat meningkatkan kualitas solusi lebih jauh.

Meskipun algoritma bf-DCQO menggunakan iterasi, ia bersifat non-variasional. Setelah setiap iterasi algoritma, distribusi state diukur. Distribusi yang diperoleh digunakan untuk menghitung apa yang disebut bias-field. Bias-field memungkinkan memulai iterasi berikutnya dari state energi mendekati solusi yang ditemukan sebelumnya. Dengan cara ini, algoritma bergerak dengan setiap iterasi menuju solusi berenergi lebih rendah. Biasanya, sekitar sepuluh iterasi sudah cukup untuk mencapai konvergensi ke solusi, secara keseluruhan memerlukan jumlah iterasi yang jauh lebih sedikit dibandingkan algoritma variasional, yang umumnya memerlukan sekitar 100 iterasi.\n

Optimizer ini menggabungkan algoritma bf-DCQO dengan pasca-pemrosesan klasik. Setelah mengukur distribusi state, dilakukan pencarian lokal. Selama pencarian lokal, bit-bit dari solusi yang diukur dibalik secara acak. Setelah pembalikan, energi dari bitstring baru dievaluasi. Jika energinya lebih rendah, bitstring tersebut disimpan sebagai solusi baru. Pencarian lokal hanya berskala linier dengan jumlah qubit; karenanya, ini murah secara komputasi. Karena pasca-pemrosesan mengoreksi bitflip lokal, ia mengkompensasi kesalahan bit-flip yang sering merupakan hasil dari ketidaksempurnaan perangkat keras dan kesalahan pembacaan.

Contoh konfigurasi kustom​

Berikut cara kamu mengonfigurasi Iskay dengan pengaturan berbeda:

custom_options = {
    "shots": 15_000,  # Higher shot count for better statistics
    "num_iterations": 12,  # More iterations for solution refinement
    "preprocessing_level": 1,  # Light preprocessing for problem simplification
    "postprocessing_level": 2,  # Maximum postprocessing for solution quality
    "transpilation_level": 2,  # Improved transpiler (default)
    "seed_transpiler": 42,  # Fixed seed for reproducible results, which skips the seed search
    "job_tags": ["custom_config"],  # Custom tracking tags
}

Optimisasi seed: Secara default, seed_transpiler adalah None, dan transpilasi level 2 menelusuri berbagai seed transpiler untuk menemukan circuit dengan depth terbaik. Jika kamu menetapkan seed, fungsi melewati pencarian itu dan transpilasinya bisa direproduksi.

Level transpilasi (1-3): Opsi transpilation_level memilih metode transpilasi.

  • Level 1: Transpiler Qiskit standar.
  • Level 2 (default): Transpiler yang ditingkatkan, yang menelusuri 15 seed transpiler dan mempertahankan circuit terbaik. Jika kamu menetapkan seed_transpiler, fungsi melewati pencarian.
  • Level 3: Line routing dengan strategi swap untuk coupling map linear yang dijelaskan di Bagian 2.2.1 Weidenfeller et al. Line routing mengikuti jadwal swap tetap, sehingga circuit depth-nya tumbuh secara linear terhadap jumlah variabel. Untuk masalah yang terhubung padat, line routing biasanya menghasilkan circuit yang lebih dangkal daripada level 1 dan 2 dan transpilasinya lebih cepat. Level 3 mendukung maksimal 127 variabel pada prosesor Heron r2 dan r3, 112 variabel pada Heron r1, dan 120 variabel pada Nighthawk.

Versi 3.0.0 menghapus level 0, 4, dan 5. Job yang meminta salah satunya gagal dengan error 1221.

Ukuran fungsi​

Setiap job berjalan pada satu ukuran, S, M, atau L. Jika ukurannya terlalu kecil, platform menolak job. Jika ukurannya lebih besar dari yang dibutuhkan job, job berjalan pada compute profile yang lebih besar daripada yang diperlukan pekerjaannya. Lihat Function sizes untuk cara kerja ukuran secara umum.

Ukuran bergantung pada dua properti modelmu, jumlah variabel dan kepadatan interaksi. Kepadatan interaksi adalah fraksi dari semua pasangan variabel yang muncul bersama dalam suatu suku dari fungsi objektif atau dari sebuah kendala.

Sebuah model harus memenuhi kedua batas dari suatu ukuran. Karena itu, model kecil dengan banyak interaksi mungkin memerlukan L. Misalnya, 10 variabel yang semuanya saling terkopel memiliki kepadatan 1,0. Setiap fungsi optimisasi memakai batas yang sama, jadi satu ukuran berarti tingkat kesulitan model yang sama di setiap fungsi.

Dua fitur model menaikkan kepadatan lebih banyak daripada yang mungkin kamu duga.

  • Suku atas lebih dari dua variabel mengopel setiap pasangan di antaranya. Misalnya, suku dalam empat variabel menyumbang keenam pasangan.

  • Sebuah kendala dihitung sebagai penalti yang menggantikannya di hardware. Kendala yang dikuadratkan mengopel setiap pasangan variabel di dalamnya, sehingga kendala one-hot atas empat variabel juga menyumbang keenam pasangan.

Jika job tidak meminta ukuran, job berjalan pada ukuran default, M.

Untuk membaca ukuran dari fungsi itu sendiri, panggil optimizer.sizes(). Untuk membaca ukuran default, panggil optimizer.get_default_size().

Hitung ukuran sebelum mengirim job​

Kalkulator hanya membaca modelmu. Kalkulator tidak mengirim job dan tidak mencadangkan apa pun, jadi kamu bisa memanggilnya sesering yang kamu perlukan sambil memperkecil model ke ukuran yang lebih kecil.

Kalkulator memerlukan paket qiskit-addon-opt-mapper. Untuk menginstalnya, jalankan perintah berikut.

# %pip install qiskit-addon-opt-mapper
"""
Size calculator for the Kipu Quantum ``iskay-quantum-optimizer`` Quantum Function.

IBM's reference ``optimization_size_calculator.py``, with ``to_optimization_problem``
implemented for the ``problem`` dict the function accepts. Everything below that function
is IBM's sizing logic and limits, unchanged, so a size means the same thing across
vendors.

Input:  the ``problem`` dict -- string-encoded index tuples to coefficients, exactly as
        ``validate_problem`` in the function parses them -- plus the other function inputs
        as ``**kwargs``::

            {"()": 1.0, "(0,)": 1.5, "(0, 3)": 2.5, "(0, 1, 2)": 4.0}

Output: ``"S"``, ``"M"`` or ``"L"``, from the number of variables and the interaction
        density: the fraction of variable pairs that appear together in a term of the
        objective or of a constraint.

``problem_type`` ("spin" or "binary") does not change which variables interact, so the
sizing is the same for both.

Constraints are sized as the penalties that replace them on hardware -- see
``_interactions``. Slack variables for inequality penalties are not counted, so a heavily
inequality-constrained model is sized slightly low on the variable count.
https://qiskit.github.io/qiskit-addon-opt-mapper/
"""
from __future__ import annotations

import ast
from collections.abc import Iterator
from itertools import combinations
from typing import Any, Literal

from qiskit_addon_opt_mapper.problems import OptimizationProblem

Size = Literal["S", "M", "L"]

# Limits are provided by IBM
_SMALL_NUMVARS, _SMALL_DENSITY = 50, 0.1
_MEDIUM_NUMVARS, _MEDIUM_DENSITY = 100, 0.25

def calculate_function_size(problem: Any, **kwargs: Any) -> Size:
    """Return the size ("S", "M" or "L") needed to run ``problem``."""
    metrics = _measure(problem, **kwargs)
    if _is_small(metrics):
        return "S"
    if _is_medium(metrics):
        return "M"
    return "L"

def to_optimization_problem(problem: Any) -> OptimizationProblem:
    """Convert the function's ``problem`` dict into an ``OptimizationProblem``.

    Keys are parsed with ``ast.literal_eval``, the same parse the function itself applies,
    so anything the function would reject raises here too rather than being sized on a
    guess. A term is classified by its distinct indices: none is the constant, one linear,
    two quadratic, three or more a higher-order term of that order.

    Indices are remapped to a dense ``0..k-1`` range, because an index that never appears
    is not a variable and gaps in the numbering must not dilute the interaction density.
    """
    if isinstance(problem, OptimizationProblem):
        return problem
    if not isinstance(problem, dict):
        raise NotImplementedError(
            f"cannot size a {type(problem).__name__}: iskay-quantum-optimizer takes a "
            "dict of string-encoded index tuples to coefficients"
        )

    terms = _parse_terms(problem)
    indices = sorted({i for support in terms for i in support})
    index_of = {index: position for position, index in enumerate(indices)}

    linear: dict[int, float] = {}
    quadratic: dict[tuple[int, int], float] = {}
    higher_order: dict[int, dict[tuple[int, ...], float]] = {}
    for support, coefficient in terms.items():
        mapped = tuple(index_of[i] for i in support)
        if len(mapped) == 1:
            linear[mapped[0]] = coefficient
        elif len(mapped) == 2:
            quadratic[mapped] = coefficient
        elif len(mapped) >= 3:
            higher_order.setdefault(len(mapped), {})[mapped] = coefficient

    converted = OptimizationProblem()
    converted.binary_var_list(len(indices), name="x")
    converted.minimize(
        constant=terms.get((), 0.0),
        linear=linear or None,
        quadratic=quadratic or None,
        higher_order=higher_order or None,
    )
    return converted

def _parse_terms(problem: dict) -> dict[tuple[int, ...], float]:
    """Map each term's sorted, distinct indices to its coefficient.

    Repeated supports (for example, "(0, 1)" and "(1, 0)") are summed; for sizing only the
    presence of the term matters.
    """
    terms: dict[tuple[int, ...], float] = {}
    for key, coefficient in problem.items():
        parsed = ast.literal_eval(key) if isinstance(key, str) else key
        if not isinstance(parsed, tuple):
            raise ValueError(f"problem key {key!r} is not a tuple")
        support = tuple(sorted(set(parsed)))
        if any(not isinstance(i, int) for i in support):
            raise ValueError(f"problem key {key!r} holds non-integer indices")
        terms[support] = terms.get(support, 0.0) + float(coefficient)
    return terms

def _measure(problem: Any, **kwargs: Any) -> dict[str, float]:  # pylint: disable=unused-argument
    """Return the number of variables and the interaction density."""
    model = to_optimization_problem(problem)
    num_vars = model.get_num_vars()

    pairs = set()
    for term in _interactions(model):
        pairs.update(frozenset(pair) for pair in combinations(set(term), 2))

    max_pairs = num_vars * (num_vars - 1) // 2
    return {
        "num_vars": num_vars,
        "density": len(pairs) / max_pairs if max_pairs else 0.0,
    }

def _interactions(problem: OptimizationProblem) -> Iterator[tuple[int, ...]]:
    """Yield the variable tuple of every term that couples two or more variables.

    Objective terms contribute their own variables; a linear objective term couples
    nothing.

    A constraint contributes the whole support of its left-hand side, because the
    unconstrained form of the model replaces it with a penalty ``w * lhs**2``, and
    squaring a sum couples every pair of variables in it -- a one-hot constraint over four
    variables becomes a clique on those four. Neither the penalty weight nor the
    right-hand side changes which pairs exist, so neither is needed here. This holds
    whether or not the function handles constraints natively, because a size has to mean
    the same thing across every optimization function.
    """
    objective = problem.objective
    yield from objective.quadratic.to_dict()
    for expression in objective.higher_order.values():
        yield from expression.to_dict()

    for constraint in problem.linear_constraints:
        yield _constraint_support(constraint)
    for constraint in problem.quadratic_constraints:
        yield _constraint_support(constraint)
    for constraint in problem.higher_order_constraints:
        yield _constraint_support(constraint)

def _constraint_support(constraint: Any) -> tuple[int, ...]:
    """Return every variable appearing in a constraint's left-hand side."""
    variables = set(constraint.linear.to_dict())
    if hasattr(constraint, "quadratic"):
        for term in constraint.quadratic.to_dict():
            variables.update(term)
    if hasattr(constraint, "higher_order"):
        for expression in constraint.higher_order.values():
            for term in expression.to_dict():
                variables.update(term)
    return tuple(variables)

def _is_small(metrics: dict[str, float]) -> bool:
    """Determine if the metrics fit T-size 'S'."""
    return (
        metrics["num_vars"] <= _SMALL_NUMVARS
        and metrics["density"] <= _SMALL_DENSITY
    )

def _is_medium(metrics: dict[str, float]) -> bool:
    """Determine if the metrics fit T-size 'M'."""
    return (
        metrics["num_vars"] <= _MEDIUM_NUMVARS
        and metrics["density"] <= _MEDIUM_DENSITY
    )

Menentukan ukuran masalah sparse​

Bayangkan sebuah cincin berisi 40 spin, di mana setiap spin hanya berinteraksi dengan dua tetangganya. Cincin ini punya 40 pasangan yang berinteraksi dari 780, yaitu kepadatan sekitar 0,05, jadi memenuhi kedua batas S.

ring = {f"({i}, {(i + 1) % 40})": 1.0 for i in range(40)}

size = calculate_function_size(ring)
print(size)

Outputnya S. Berikan hasilnya ke run.

job = optimizer.run(
    problem=ring,
    problem_type="spin",
    backend_name=backend_name,  # such as "ibm_fez"
    options={"shots": 5000, "num_iterations": 5},
    function_size=size,
)
print(job.job_id)

Jika ukurannya terlalu kecil, job gagal dengan error 4600, dan pesan error menyebutkan ukuran yang harus dipakai. Jika ukurannya lebih besar dari yang dibutuhkan job, job berjalan normal dan mencatat event advisory 4601. Lihat Function sizes untuk mempelajari lebih lanjut.

Contoh 1: Fungsi biaya sederhana​

Perhatikan fungsi biaya dalam formulasi spin:

C(x0,...,x6)=3+x0−x1+2x2+x3−2x4+x5−x6+2x0x1−x1x2C(x_0, ..., x_6) = 3 + x_0 - x_1 + 2x_2 + x_3 - 2x_4 + x_5 - x_6 + 2x_0x_1 - x_1x_2C(x0​,...,x6​)=3+x0​−x1​+2x2​+x3​−2x4​+x5​−x6​+2x0​x1​−x1​x2​

where (x0,...,x6)∈{−1,1}7(x_0, ..., x_6) \in \{-1, 1\}^7(x0​,...,x6​)∈{−1,1}7.

Solusi untuk fungsi biaya sederhana ini adalah

dengan nilai minimum C∗=−7C^{*} = -7C∗=−7

Kita mulai dengan membuat dictionary berisi koefisien fungsi objektif sebagai berikut:

Kita selesaikan masalahnya dengan menjalankan optimizer. Karena (x0,...,x6)∈{−1,1}7(x_0, ..., x_6) \in \{-1, 1\}^7(x0​,...,x6​)∈{−1,1}7, kita harus mengatur problem_type=spin.

options = {"shots": 5000, "num_iterations": 5, "use_session": True}

Contoh 2: MaxCut​

Banyak masalah graf seperti MaxCut atau Maximum Independent Set adalah masalah NP-hard dan merupakan kandidat ideal untuk menguji algoritma dan perangkat keras kuantum. Contoh ini menunjukkan cara menyelesaikan masalah MaxCut pada graf 3-regular menggunakan Quantum Optimizer.

Untuk menjalankan contoh ini, kamu harus menginstal paket networkx selain qiskit-ibm-catalog. Untuk menginstalnya, jalankan perintah berikut:

# %pip install networkx numpy

1. Buat fungsi objektif​

Mulai dengan membuat graf 3-regular acak. Untuk graf ini, kita definisikan fungsi objektif dari masalah MaxCut.

import networkx as nx

# Create a random 3-regular graph
G = nx.random_regular_graph(3, 10, seed=42)

# Create the objective function for MaxCut in Ising formulation
def graph_to_ising_maxcut(G):
    """
    Convert a NetworkX graph to an Ising Hamiltonian for the max-cut problem.
    Args:
        G (networkx.Graph): The input graph.
    Returns:
        dict: The objective function of the Ising model
    """
    # Initialize the linear and quadratic coefficients
    objective_func = {}
    # Populate the coefficients
    for i, j in G.edges:
        objective_func[f"({i}, {j})"] = 0.5
    return objective_func

objective_func = graph_to_ising_maxcut(G)

Hitung function size untuk masalah ini.

size = calculate_function_size(objective_func)
print(size)

Outputnya L. Grafnya punya 10 node dan 15 edge, jadi 15 dari 45 pasangan variabel berinteraksi. Kepadatan sekitar 0,33 ini lebih tinggi daripada batas M.

2. Jalankan Optimizer​

Selesaikan masalahnya dengan menjalankan optimizer.

options = {"shots": 5000, "num_iterations": 5, "use_session": True}

arguments = {
    "problem": objective_func,
    "problem_type": "spin",
    "backend_name": backend_name,  # such as "ibm_fez"
    "options": options,
    "function_size": size,
}

job = optimizer.run(**arguments)

3. Ambil hasilnya​

Ambil hasilnya dan petakan bitstring solusi kembali ke node graf aslinya.

print(job.result())

Solusi untuk masalah Maxcut langsung terdapat dalam sub-dictionary solution dari objek hasil

maxcut_solution = job.result()["solution"]

Untuk mereproduksi performa benchmark pada instance HUBO, pilih backend ibm_marrakesh dan atur direct_qubit_mapping ke True pada sub-dictionary options. Contoh berikut menjalankan instance Maxcut dengan 150 node.

from github import Github
import urllib
import json

repo = "Kipu-Quantum-GmbH/benchmark-instances"
path = "maxcut/maxcut_regular_3_150_nodes_weighted.json"
gh = Github()
repo = gh.get_repo(repo)
branch = "main"
file = repo.get_contents(urllib.parse.quote(path), ref=branch)

# load json file with benchmark problem
problem_json = json.loads(file.decoded_content)

# convert objective function to compatible format
objective_func = {
    key: ast.literal_eval(value) for key, value in problem_json.items()
}

# Calculate the function size. The problem has 150 variables,
# more than the M bound allows, so the size is "L".
size = calculate_function_size(objective_func)

# Setup configuration to run the optimizer
options = {
    "shots": 5_000,
    "num_iterations": 5,
    "use_session": True,
    "direct_qubit_mapping": False,
}

arguments = {
    "problem": objective_func,
    "problem_type": "spin",
    "backend_name": "<BACKEND-NAME>",
    "options": options,
    "function_size": size,
}

job = optimizer.run(**arguments)

result = job.result()
