Tool untuk memprofil, menyesuaikan, dan memeriksa eksperimen

Perkiraan penggunaan: 10 menit pada prosesor Heron r2 (CATATAN: Ini hanya perkiraan. Waktu runtime kamu mungkin berbeda.)

Untuk mendapat hasil bagus dari komputer kuantum, kamu butuh lebih dari sekadar circuit yang dirancang dengan baik. Kondisi device saat ini, cara circuit dijadwalkan, noise yang dialami circuit, serta kapan dan bagaimana job kamu berjalan di quantum processing unit (QPU) semuanya memengaruhi kualitas hasil. Qiskit dan IBM Quantum® Compute Service menawarkan kumpulan tool developer yang terus bertambah dan mengungkap informasi ini. Kamu bisa memakai tool ini untuk bertindak berdasarkan informasi itu sebelum mengeluarkan waktu QPU untuk eksperimen penuh, dan untuk men-debug eksperimen yang sudah selesai.

Tutorial ini memakai satu eksperimen end-to-end untuk menunjukkan cara menggabungkan tool-tool ini di setiap tahap alur kerja pengembangan yang umum. Tidak semua tool berguna untuk setiap eksperimen, jadi pilih tool yang menjawab pertanyaan yang kamu punya tentang workload-mu sendiri.

Alur kerjanya sebagai berikut:

  1. Siapkan circuit mirror dari evolusi waktu Trotter model Ising medan-transversal linear.

  2. Pilih backend dengan set data kalibrasi alternatif yang dirancang untuk metode mitigasi error berbasis model noise.

  3. Jalankan eksperimen benchmarking device agar transpiler memakai properti device terbaru saat memilih layout.

  4. Periksa informasi timing dari circuit yang dijadwalkan.

  5. Pelajari model noise Pauli-Lindblad dan readout untuk circuit.

  6. Jalankan simulasi lokal tanpa noise, tanpa mitigasi, dan dengan mitigasi. Simulasi ber-noise memakai model noise yang dipelajari untuk menunjukkan seberapa besar peningkatan yang mungkin kamu peroleh dari metode mitigasi error yang dipilih. Tutorial ini memakai probabilistic error cancellation (PEC) dan Twirled Readout Error eXtinction (TREX).

  7. Dapatkan perkiraan penggunaan tanpa menjalankan di QPU, untuk memeriksa apakah kamu perlu menyesuaikan eksperimen agar sesuai anggaran.

  8. Mulai session dan picu kalibrasi agar eksperimen memakai data kalibrasi terbaru.

  9. Jalankan eksperimen di QPU dengan Estimator, dan bandingkan hasil hardware dengan pratinjau simulasi.

  10. Periksa execution span untuk melihat apakah ada celah signifikan di antara kelompok eksekusi (chunk).

Persyaratan​

Sebelum memulai tutorial ini, pastikan kamu sudah menginstal yang berikut:

  • Qiskit SDK v2.3 atau lebih baru, dengan dukungan visualization

  • qiskit-ibm-runtime v0.52.1 or later (pip install qiskit-ibm-runtime)

  • Qiskit Aer (pip install qiskit-aer)

  • Plotly (pip install plotly)

  • Qiskit Device Benchmarking (pip install git+https://github.com/qiskit-community/qiskit-device-benchmarking.git)

Persyaratan plan

Beberapa langkah dalam tutorial ini tidak tersedia di setiap plan:

  • Job dry-run (Langkah 2.4 dan 3.5) hanya tersedia di plan Flex, Premium, dan On-Prem.

  • Session (Langkah 4.1) tidak tersedia di Open Plan. Untuk menjalankan dalam batch mode, atur run_calibration = False di Langkah 4.1.

Langkah 1: Tentukan circuit dan observable​

Siapkan circuit mirror dari evolusi waktu Trotter model Ising medan-transversal linear. Cerminkan circuit untuk membatalkan unitary circuit dan membentuk circuit identitas. Karena keluaran idealnya adalah state semua-nol, nilai ekspektasi ideal tiap observable ZZZ satu-qubit adalah 1. Pencerminan juga menggandakan kedalaman circuit, yang memperkuat efek noise.

import numpy as np
from qiskit.circuit import QuantumCircuit
from qiskit.quantum_info import SparsePauliOp

def construct_ising_circuit(
    num_qubits: int,
    num_trotter_steps: int,
    rx_angle: float,
    barrier: bool = True,
) -> QuantumCircuit:
    circuit = QuantumCircuit(num_qubits)

    for _step in range(num_trotter_steps):
        circuit.rx(rx_angle, range(num_qubits))
        if barrier:
            circuit.barrier()
        for first_qubit in (1, 2):
            for idx in range(first_qubit, num_qubits, 2):
                # equivalent to Rzz(-pi/2):
                circuit.sdg([idx - 1, idx])
                circuit.cz(idx - 1, idx)
        if barrier:
            circuit.barrier()

    return circuit

def mirror_circuit(circuit: QuantumCircuit) -> QuantumCircuit:
    mirror_circ = circuit.copy_empty_like()
    mirror_circ.compose(circuit, inplace=True)
    mirror_circ.barrier()
    mirror_circ.compose(circuit.inverse(), inplace=True)
    mirror_circ.measure_active()
    return mirror_circ
num_qubits = 20
observables = [
    SparsePauliOp("I" * ((num_qubits - 1) - q) + "Z" + "I" * q)
    for q in range(num_qubits)
]

# Free parameters of the demonstration circuit: the number of Trotter steps
# sets the circuit depth, and rx_angle is the transverse-field rotation angle
# applied in each step (pi/4 makes the dynamics non-Clifford)
num_trotter_steps = 5
rx_angle = np.pi / 4

circuit = construct_ising_circuit(
    num_qubits, num_trotter_steps, rx_angle, barrier=False
)
mirrored_circuit = mirror_circuit(circuit)
mirrored_circuit.draw(
    "mpl", fold=-1, scale=0.3, idle_wires=False, measure_arrows=False
)

Langkah 2: Optimalkan untuk eksekusi di hardware kuantum​

2.1 Gunakan kalibrasi alternatif jika berlaku​

IBM® mengalibrasi QPU-nya secara berkala untuk performa yang baik di berbagai kasus penggunaan umum. Namun, beberapa workload diuntungkan oleh instruksi yang parameternya disetel berbeda. Untuk informasi lebih lanjut, lihat Specially calibrated instructions.

Tutorial ini memakai set data kalibrasi alternatif bernama slow_gates_ac. Kalibrasi ini berisi gate cz yang lebih lambat dan memodulasi bias two-level system (TLS) untuk menstabilkan error device dari waktu ke waktu. Perubahan ini menguntungkan metode mitigasi error yang bergantung pada model noise yang dipelajari. Kalibrasi slow_gates_ac hanya tersedia di QPU Heron. Jika kamu menjalankan di QPU Nighthawk, pakai slow_gates sebagai gantinya.

from qiskit_ibm_runtime import QiskitRuntimeService

service = QiskitRuntimeService()
# Use slow_gates_ac because this tutorial uses a noise-learning-based mitigation method
backend = service.backend("ibm_kingston", calibration_id="slow_gates_ac")

2.2 Jalankan benchmarking device real-time​

Salah satu tahap transpilasi yang paling kritis adalah pemilihan layout, yang memetakan qubit virtual di circuit ke qubit fisik di device target. Layout yang baik meminimalkan jumlah operasi SWAP yang dibutuhkan dan menempatkan circuit pada qubit dengan performa terbaik, jadi kualitas layout awal bisa sangat memengaruhi kualitas hasil kamu.

Rutinitas benchmarking berkala berjalan di setiap QPU IBM untuk melaporkan performa terkini qubit-nya: waktu relaksasi (T1T_1T1​), waktu koherensi (T2T_2T2​), error readout, dan error gate satu- dan dua-qubit. Transpiler Qiskit memakai metrik ini saat memilih layout.

Namun, properti qubit superkonduktor bisa bergeser dalam skala waktu yang lebih pendek, dan cacat sementara, yang dikenal sebagai TLS, dapat menurunkan sementara kualitas qubit yang tadinya bagus saat kalibrasi. Jika transpiler memakai informasi yang usang, ia tidak bisa memilih layout terbaik. Karena itu, mungkin layak mengorbankan sedikit waktu QPU untuk mengkarakterisasi device sebelum kamu memilih layout.

Lihat tutorial Refresh backend properties with real-time benchmarking untuk panduan lengkapnya. Suite karakterisasi membangun beberapa eksperimen, mengirim banyak job, dan mem-fit hasilnya. Proses ini bisa memakan beberapa menit secara total. Aktifkan logging level INFO agar setiap tahap mencetak progresnya saat berjalan.

import sys
import logging

logger = logging.getLogger("qiskit_device_benchmarking")

2.4 Visualisasikan timing circuit​

Selain instruksi dalam circuit, kamu mungkin ingin memvisualisasikan jadwal circuit, untuk menemukan waktu menganggur pada qubit atau penyelarasan instruksi yang tidak efisien. Kamu bisa mendapat informasi timing paling detail dan akurat dari IBM Quantum Compute Service dengan memakai mode dry-run.

Circuit dalam tutorial ini bersifat statis, jadi jadwalnya tidak terlalu informatif. Kamu bisa mendapatkan informasi timing serupa secara lokal dari circuit dan properti backend, misalnya dengan timeline drawer bawaan Qiskit. Tutorial ini menyertakan langkah ini untuk menunjukkan cara meminta dan memvisualisasikan informasi timing. Informasi timing dari layanan paling berguna untuk dynamic circuit. Dynamic circuit berisi pengukuran di tengah circuit, operasi kondisional, dan feedforward, yang menambahkan operasi implisit seperti menyiarkan hasil pengukuran dan menentukan cabang. Timing operasi-operasi ini tidak bisa ditentukan dari circuit dan properti backend saja.

Lihat Visualize circuit timing untuk informasi lebih lanjut. Timing circuit terjadwal hanya tersedia untuk job Sampler dan Executor, jadi sel berikut mengirimkan circuit dalam mode dry-run menggunakan Sampler. Job yang kamu kirim dalam mode dry-run tidak berjalan di QPU sungguhan dan tidak dikenai biaya.

from qiskit_ibm_runtime.executor_sampler import Sampler

Langkah 3: Terapkan error mitigation dan uji secara lokal​

3.1 Cliffordize circuit​

Biaya simulasi noisy secara umum tumbuh secara eksponensial terhadap jumlah qubit, dan sebagian besar laptop tidak bisa mensimulasikan lebih dari sekitar 32 qubit. Karena itu, ubah dulu circuit menjadi circuit Clifford, yang bisa ditangani simulator stabilizer jauh lebih efisien. Konversi ini membulatkan setiap sudut rotasi ke sudut Clifford, sehingga circuit yang disimulasikan hanya mendekati circuit aslinya, bukan mereproduksinya.

from qiskit.transpiler import PassManager
from qiskit_ibm_runtime.transpiler.passes import ConvertISAToClifford

clifford_circuit = PassManager([ConvertISAToClifford()]).run(isa_circuit)
clifford_pubs = [(clifford_circuit, isa_observables)]

3.2 Terapkan PEC dengan TREX​

Memilih metode error mitigation yang menyeimbangkan biaya dan akurasi untuk eksperimen spesifikmu bisa jadi sulit. Kamu bisa memakai skill agen AI select-error-mitigation untuk menganalisis metode yang tersedia untuk workload kamu. Skill ini menyajikan laporan ringkasan yang menjelaskan apakah setiap metode dipilih dan alasannya.

Lihat repositori GitHub Qiskit AI skills untuk informasi lebih lanjut. Tutorial ini memakai PEC dengan TREX secara langsung, jadi kamu bisa menyelesaikannya tanpa agen AI.

PEC adalah teknik yang memitigasi noise kuantum saat kamu menghitung nilai ekspektasi observable. Dalam kondisi ideal, PEC bisa menghasilkan estimasi nilai ekspektasi yang tidak bias. PEC mempelajari noise tiap layer Gate dua-qubit, lalu menjalankan ensemble circuit yang, secara rata-rata, menerapkan invers dari noise tersebut. PEC memakai Pauli twirling untuk menyesuaikan noise menjadi channel Pauli, yang bisa dipelajari dan diinvers secara efisien.

Dalam praktiknya, PEC hanya seakurat model noise yang dipelajari. Model sparse Pauli-Lindblad hanya menyertakan suku error satu- dan dua-qubit pada qubit bertetangga, dan tidak bisa sepenuhnya menangkap efek seperti crosstalk antar qubit yang berjauhan atau error yang berkorelasi waktu. Noise perangkat juga bisa bergeser antara pembelajaran noise dan eksekusi. PEC tidak membatalkan noise yang terlewat oleh model, dan ia mengompensasi berlebihan noise yang diestimasi terlalu tinggi oleh model. Karena itu, hasil yang sudah dimitigasi masih bisa menyimpang dari nilai ideal ke kedua arah.

TREX adalah teknik yang memitigasi error pengukuran, dan berguna saat kamu mengestimasi nilai ekspektasi observable Pauli. TREX mengandalkan measurement twirling, yang mendiagonalkan matriks transfer readout-error sehingga mudah diinvers. TREX mempelajari suku penskalaan ulang dari channel noise diagonal dengan mengukur circuit kalibrasi ter-twirl yang diinisialisasi dalam state nol. Kamu bisa mengaktifkan PEC dan TREX sekaligus dengan mengatur opsi Estimator. Tutorial ini memakai implementasi sisi klien dari antarmuka Qiskit SamplerV2 dan EstimatorV2, yang diperkenalkan di qiskit-ibm-runtime v0.50.0. Primitive sisi klien ini melakukan sebagian besar pra- dan pasca-pemrosesan secara lokal dan mendelegasikan eksekusi ke primitive Executor. Saat primitive berjalan di sisi klien, kamu mendapat transparansi lebih besar, umpan balik lebih cepat saat debugging, dan kontrol yang lebih halus.

Primitive sisi klien mengimplementasikan API yang sama dengan primitive sisi server lama. Karena itu, biasanya kamu bisa beralih ke primitive sisi klien hanya dengan mengubah pernyataan import. Aktifkan logging level INFO untuk melihat progres pra- dan pasca-pemrosesan sisi klien.

import logging

logger = logging.getLogger("qiskit_ibm_runtime")
logger.setLevel(logging.INFO)
from qiskit_ibm_runtime.executor_estimator import Estimator

estimator = Estimator(mode=backend)
# Enable TREX
estimator.options.resilience.measure_mitigation = True
# Enable PEC
estimator.options.resilience.pec_mitigation = True

3.3 Pelajari model noise dan jalankan circuit yang sudah di-Cliffordize​

PEC dan TREX sama-sama memerlukan pembelajaran noise, yang bisa kamu lakukan dengan NoiseLearnerV3. Langkah-langkahnya sebagai berikut:

  1. Temukan layer Gate dua-qubit dan layer pengukuran yang unik di circuit, masing-masing untuk protokol Pauli-Lindblad dan TREX.

  2. Berikan layer tersebut ke NoiseLearnerV3 untuk mempelajari model noise.

  3. Ubah model noise yang dipelajari menjadi peta Pauli-Lindblad.

Estimator tidak memakai model noise TREX yang sudah dipelajari sebelumnya. Sebaliknya, ia melakukan pembelajaran TREX sendiri. Kode berikut tetap mempelajari kedua model, karena simulasi noisy memakai model readout yang dipelajari.

Lihat Noise learning helper untuk informasi lebih lanjut tentang NoiseLearnerV3. Selain eksperimen pembelajaran noise, jalankan circuit yang sudah di-Cliffordize di QPU. Langkah ini tidak selalu diperlukan, tapi memberi pembanding untuk hasil simulasi di Langkah 3.4.4. Jalankan keduanya dalam satu batch untuk meminimalkan pergeseran profil noise di antara keduanya.

4.4 Periksa execution span​

Saat kamu mengirim circuit dengan banyak konfigurasi, seperti pada gate twirling, IBM Quantum Compute Service tidak selalu menjalankan semua konfigurasi circuit sekaligus. Sebaliknya, layanan mengelompokkannya menjadi chunk dan menjalankan satu chunk per shot loop. Shot loop adalah satu putaran eksekusi di hardware kuantum, di mana setiap circuit dalam chunk dijalankan sebanyak shot yang diminta.

Semua job yang dikirim ke QPU sungguhan memerlukan pra-pemrosesan klasik, seperti penerjemahan menjadi pulse yang bisa dikirim ke hardware. Karena pra-pemrosesan ini bisa dilakukan secara paralel, layanan men-dequeue dan memulai beberapa job sekaligus. Namun, QPU hanya bisa memproses satu unit kerja pada satu waktu. Karena itu, kalau job kamu menghasilkan banyak chunk, chunk tersebut mungkin diselang-seling dengan chunk dari job pengguna lain, dan setiap chunk mungkin harus menunggu gilirannya di QPU.

Metadata hasil job melaporkan timing eksekusi QPU untuk setiap chunk. Visualisasi berikut menunjukkan apakah ada jeda signifikan antara eksekusi chunk dalam job kamu. Kalau jedanya lebih lebar dari yang bisa ditoleransi eksperimenmu, kamu mungkin perlu menjalankan ulang job, atau memakai session execution mode, yang memberi workload kamu akses eksklusif ke QPU.

Lihat View execution spans untuk informasi lebih lanjut.

Rekomendasi
  • Jalankan ulang eksperimen dengan dan tanpa kalibrasi slow_gates_ac (Langkah 2.1), properti perangkat yang disegarkan (Langkah 2.2), atau kalibrasi session (Langkah 4.1) untuk mengukur seberapa besar tiap alat memperbaiki hasil untuk workload kamu.
  • Coba metode error mitigation yang lebih murah seperti zero-noise extrapolation (ZNE), dan pakai simulasi lokal serta estimasi penggunaan dry-run untuk membandingkan biaya dan akurasinya dengan PEC. Skill agen AI select-error-mitigation bisa membantu kamu memilih.
  • Jelajahi seluruh suite karakterisasi, termasuk randomized benchmarking, di tutorial Refresh backend properties with real-time benchmarking.
  • Pelajari lebih lanjut tentang primitive sisi klien dan Executor di Migrate from server-side to client-side Sampler and Estimator.
  • Terapkan alat-alat ini pada eksperimen kamu sendiri. Mulai dari alat yang menangani sumber ketidakpastian terbesar kamu, seperti kualitas perangkat, noise, biaya, atau timing eksekusi.
